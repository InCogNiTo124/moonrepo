Basic steps are usually these:

## 1. Merge all updates with jj

It's best to use the following command:

```shell
jj git fetch && jj new main@origin 'remote_bookmarks(glob:"renovate/*")' -m 'chore(deps): Bump all'
```

This command fetches all commits and merges all the updates into a single "octopus" merge (in git terminology) aka megamerge (in jj terminology).

### 1.1 Possible merge conflicts

It's rare, but possible, to get merge conflicts. Rules for resolving them are generally:

* delete all lock files (it's hard to resolve these, and they're generated by the tooling anyways)
* merge all package config files such that we keep the latest version.
  * while this is super easy to do when the two conflicting versions share a major version, it tends to get messy if one version is a major bump.
  * for now, until further notice, don't stop updating major bumps, i.e. if for example there's a conflict between 7.9.1 and 8.0.0, choose 8.0.0

We're gonna generate the lock files in the next step

## 2. Testing the build

Since we use moon to govern this monorepo, run the following command to try to build everything:

```shell
moon run :build
```

Moon should be smart enough to cache things that did not change.

### Known issues

* `libsqlite3-sys` version in `//personal-blog/database` sometimes conflicts with `diesel`, since they release on a different cadence. If this happens, just manually bump the version down, i.e. to the previous version.

## 3. Publish

I usually just YOLO things to `main` branch, but *not dependency updates*. For this, I take an extra step of pushing and making a PR. To publish work, run:

```shell
jj git push -c @
```

(make sure you did not check some other jj change, the mega merge change with dep bumps should be @)

IMPORTANT: Once that is done, and only after user's explicit approval, you may run `jj bookmark set -r <jj change id>` and `jj git push -b main`. You do not run it unless the user has explicitly consented, though.
