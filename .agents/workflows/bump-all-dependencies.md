Basic steps are usually these:

## 1. Merge all updates with jj

It's best to use the following command:

```shell
jj git fetch && jj new main@origin 'remote_bookmarks(glob:"renovate/*")' -m 'chore(deps): Bump all'
```

This command fetches all commits and merges all the updates into a single "octopus" merge (in git terminology) aka megamerge (in jj terminology).

### 1.1 Possible merge conflicts

It's rare, but possible, to get merge conflicts. Rules for resolving them are generally:

* delete all lock files (it's hard to resolve these, and they're generated by the tooling anyways)
* merge all package config files such that we keep the latest version.
  * For `.prototools` conflicts, choose the highest resolved version for each tool (e.g. `moon`, `bun`, `rust`, `uv`).
  * while this is super easy to do when the two conflicting versions share a major version, it tends to get messy if one version is a major bump.
  * for now, until further notice, don't stop updating major bumps, i.e. if for example there's a conflict between 7.9.1 and 8.0.0, choose 8.0.0

We're gonna generate the lock files in the next step.

### 1.2 Preparing the toolchain and environment

After resolving conflicts in `.prototools`, perform the following steps to update the environment:

1. **Install tools via proto**:
   Run `proto use` to download and install the new toolchain versions defined in `.prototools`.
2. **Install target dependencies for Rust**:
   When the Rust version is bumped, you must install the compilation targets (e.g., `wasm32-unknown-unknown` and `x86_64-unknown-linux-musl`) for the newly installed rustup toolchain version:
   ```shell
   rustup target add --toolchain <new_rust_version>-x86_64-unknown-linux-gnu wasm32-unknown-unknown x86_64-unknown-linux-musl
   ```

## 2. Testing the build

Since we use moon to govern this monorepo, run the following command to try to build everything:

```shell
moon run :build
```

Moon should be smart enough to cache things that did not change.

### Known issues

* `libsqlite3-sys` version in `//personal-blog/database` sometimes conflicts with `diesel`, since they release on a different cadence. If this happens:
  1. Manually bump the version down in `personal-blog/database/Cargo.toml` (e.g., to `0.36.0`).
  2. Run `cargo update` in the `personal-blog/database` directory to regenerate `Cargo.lock`. (Since cargo tasks are run with `--locked`, the lockfile must be kept in sync manually).
* When updating the Rust toolchain version, make sure to update it in **all three places**:
  1. `.prototools` (the source of truth for proto/moon)
  2. `.moon/toolchains.yml`
  3. `.github/workflows/ci.yml` — the `channel` field in the `moonrepo/setup-rust` step (this ensures Rust targets are installed on the correct toolchain, not `stable`)
* **Bun `file:` dependencies and moon's InstallDeps**: Moon runs `bun install` for all JS projects before any tasks. Projects with `file:` deps on build outputs (e.g., brachi → brachistochrone_solver/pkg, personal-website → personal-reusables) will fail because the output doesn't exist yet. Workarounds:
  - For wasm packages: a stub `package.json` is created in CI (see `.github/workflows/ci.yml`)
  - For SvelteKit libraries: use `kit.alias` in `svelte.config.js` pointing to the source (see `personal-website/svelte.config.js`)
  - Upstream issue: https://github.com/moonrepo/moon/issues/2538

## 3. Publish

I usually just YOLO things to `main` branch, but *not dependency updates*. For this, I take an extra step of pushing and making a PR. To publish work, run:

```shell
jj git push -c @
```

(make sure you did not check some other jj change, the mega merge change with dep bumps should be @)

IMPORTANT: Once that is done, and only after user's explicit approval, you may run `jj bookmark set -r <jj change id>` and `jj git push -b main`. You do not run it unless the user has explicitly consented, though.
